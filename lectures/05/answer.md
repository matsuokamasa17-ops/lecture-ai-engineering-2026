## 宿題

### 取り組んだレベル

基礎

### やったこと

`app/config.py` の `RAG_TOP_K` を変更し、同じ質問を
`--trace`付きで変更前後に実行して比較した。

- 変更前：`RAG_TOP_K = 5`
- 変更後：`RAG_TOP_K = 3`

### 比較した質問と条件

質問：

> 第2回の説明では、LoRAは何を固定し何を学習しますか？  
> QLoRAは何を加えますか？

条件：

- 使用モデル：`gemini-3.5-flash-lite`
- 対象資料：第1回〜第3回の講義資料
- 実行方法：`uv run python -m app.agent --trace`
- 検索ツール：`search_materials`

### 結果

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| `RAG_TOP_K` | 5 | 3 |
| 検索ツール | `search_materials` | `search_materials` |
| 根拠 | 第2回 p.51、p.52 | 第2回 p.51、p.52 |
| 回答 | 正確 | 正確 |
| 処理時間 | 40.04秒 | 28.45秒 |
| 入力トークン | 3,028 | 2,080 |
| 出力トークン | 202 | 210 |
| 推定費用 | $0.001413 | $0.001149 |

### 改善した例と、残る失敗・制約

#### 改善した例

`RAG_TOP_K`を5から3に変更しても、今回の質問では必要な
第2回p.51・p.52を維持できた。

入力トークン数は3,028から2,080に減少し、推定費用も
$0.001413から$0.001149に減少した。

#### 残る失敗・制約

今回はLoRA・QLoRAに関する1問だけで確認したため、
他の質問でも必要な根拠が残るかは確認できていない。

`RAG_TOP_K`を小さくすると、複数ページを必要とする質問では
必要なページが検索結果から漏れる可能性がある。

また、処理時間はAPIの混雑状況などによって変動する。

### 気づき・疑問

検索結果を少なくしても、上位の検索結果だけで答えられる質問では、
回答の正確さを保ちながら入力情報量と費用を削減できることが分かった。

一方で、質問に必要なページ数は質問ごとに異なるため、
常に`RAG_TOP_K = 3`が適切とは限らないと考えた。

複数ページを必要とする質問では、根拠を漏らさず、
入力情報量も抑えられる`RAG_TOP_K`の値がいくつなのか疑問に思った。
